推荐分工与成果目标

学生 A · 系统与执行

故障域感知的确定性共享执行与原生转账调度

核心问题：多验证者能否在明确的信任与故障边界下复用同一份执行结果，并通过依赖调度和不可变输出降低重复计算，而不改变既有交易语义？

交付：可复用的执行服务、结果身份与接管协议、直接转账执行器、跨实现等价测试、具有安全条件的部署指南。

主要科学贡献：共享执行的适用条件与失效边界，以及在冲突、换主、取消和分叉下可证明且可测量的复用机制。

学生 B · 数据库与可靠性

QMDB 认证状态的跨实现一致性与崩溃安全有界流水

核心问题：在高吞吐和故障恢复下，如何让三种客户端对状态转移、QMDB 根、提交证据与持久化边界保持一致，同时给积压、内存和恢复成本建立可验证的界限？

交付：状态转移契约、版本化 QMDB 发布与恢复协议、有界信用控制、差分故障测试平台、快照和历史查询的可验证接口。

主要科学贡献：跨执行、认证状态与 BFT 投票持久化的组合正确性，以及安全边界内的吞吐与尾延迟优化。

重大成果目标：形成可推广的方法、论证和开源系统证据，争取高水平系统／数据库／安全论文及被三个工程长期采用的组件。高 TPS、完成一次移植或发现几个 bug 都不足以单独构成重大研究成果；论文录用与性能增益取决于后续实验。

两人的共同接口是带完整身份的不可变执行产物：A 负责如何正确生成与共享，B 负责如何认证、发布、持久化和恢复。各自维护独立基线和论文主结论，联合实验另行报告贡献。

近期研究给出的方向与尚待解决的缺口

动向与时间核对的一手研究对 N42 的启发与适用限制
认证存储，2025QMDB 将 KV 与 Merkle 存储统一，利用 append-only twig 设计降低更新 IO。复用现有 bin 树；研究焦点放在跨实现转移语义、版本发布和恢复。论文数据库更新速率不能直接解释为整链 TPS。
端到端流水，2025Zaptos 重叠执行、认证和提交，研究整链延迟；Monad 文档 描述共识与执行解耦。比较端到端关键路径和状态滞后。首先保持 H2 wire 与提交语义，协议级延期执行仅作后期扩展，不直接复制另一条链的规则。
冲突执行，2025NEMO 使用对象模型、读写提示和优先调度减少高冲突重复工作；结果来自模拟执行实验。把依赖提示与实际验证结合，测热点账户、自转账和共享收款人。对象模型不能未经转换就套用到 N42 的账户／nonce 模型。
传播鲁棒性，2025Raptr 用 prefix consensus 研究高吞吐 BFT 的传播与网络故障鲁棒性。把缺帧补取、数据可用性与背压列为首等实验条件；先优化现有 H2 数据路径，是否改共识取决于证据。
自适应调度，2026-09Barnacle 根据已提交 DAG 的确定性观测自适应调整 leader 数。启发有界信用控制的可验证反馈设计。它面向 DAG 多 leader，N42 当前 H2 调度不能直接视为同一算法。
恢复与 quorum，2026-10Stateless Recovery / Quorum Safety 分析保留密钥而丢失协议状态的恢复，强调签名释放前持久化投票记录。把 R1／R2 水位和 lock 与 QMDB 恢复组成联合模型。其单步证书结果不是完整 H2 安全证明，需要检验具体协议前提。
成熟并行基准Block-STM 在预定交易顺序下通过执行／验证调度保持确定性。作为执行调度对照；部署不同的对象、存储或 VM 时报告差异，不引用其原始 TPS 作为公平同机对比。

研究判断：单独提高执行并行度、优化树哈希或减少共识轮次已有大量工作。更适合本项目的切口，是把执行复用的信任条件与跨客户端状态／持久化的组合约束明确建模，再在真实高吞吐链中验证。这是候选创新方向，需在开题前对全文和相关工作开展系统查新。

课题一 · 建议由 Rust / 并发系统背景学生承担

故障域感知的确定性共享执行与原生转账调度

英文暂定：Fault-Domain-Aware Deterministic Shared Execution for High-Throughput Blockchains

1. 可独立成论文的主问题

在既有交易顺序与 H2 协议下，为一组属于同一可信执行域的验证者构造执行复用协议：当并发请求、换主、取消、分叉和恢复发生时，哪些请求可以安全复用结果，如何限制重复工作与内存，以及怎样量化共享服务造成的关联故障？

核心假设 H-A：完整执行身份、带代际 fencing 的 owner 接管和不可变输出发布，可将健康路径同块执行次数降到每执行域一次，并在冲突负载下提高成功提交吞吐或降低尾延迟；恢复期间允许必要重算，不追求跨崩溃的绝对“恰好一次”。

2. 信任与故障模型必须先写清楚

同一执行结果的 hash 一致，只能说明结果相同，不能证明执行正确。同机七个私钥也不等于七个独立故障域。第一阶段假设共享执行组件可信、可 crash-stop；若执行服务可能返回恶意错误，必须由其他独立执行域验证，或退回独立执行。检测到差异后重执行，不能补救已经签出的错误结果。
  • 单机 E1／七验证者用于量化复用效果，清楚标注共同宿主、内核、内存和执行组件故障。
  • 多机生产模型按执行域标识和实际验证者权重计量故障预算；域被攻陷或域内多个身份失去安全状态时，将受影响身份纳入 BFT 假设，不能把共享域当成一个无权重故障。
  • 保留各验证者自己的验签、lock、投票水位与持久化签名流程。复用执行不合并 BLS 私钥，不削弱 quorum，不改变 QC 签名域。
  • 如预算只有一台服务器，成果限于受控 crash-stop 原型和模型验证；跨主机安全／性能结论需要独立多机实验。

3. 拟研究机制

ExecutionKey = H(chain/genesis, protocol & fork configuration, parent hash & state version, ordered authenticated transaction commitment, block execution environment, execution-rules version)

执行身份须覆盖 timestamp、费用参数、gas 限额、beneficiary、奖励／withdrawal 等影响执行的字段。源码版本相同不等于执行规则相同；升级时使规则版本参与身份。封头改变区块 hash 后，通过已验证的执行内容绑定原产物，不能仅按交易列表复用。

注册绑定精确父状态与认证输入获得 owner代际 token + 有界等待者执行 / 校验确定顺序与失败语义冻结输出状态差分、回执、根与读视图发布 / 复用与 canonical 身份关联撤销 / 接管旧 owner 不能晚到发布
  • 共享执行：从 n42-rs 的 import_once、built_executions 和 chain_alias 出发，建立覆盖 own／foreign／compact／payload 入口的一致状态机，处理接管、取消和引用释放。
  • 直接转账：对经过资格判定的普通转账直接更新余额、nonce、费用、gas 和回执；sender 依赖分组，显式处理 sender/recipient 交叉、费用收款人热点、溢出及自转账。合约、特殊 fork 效果和不满足条件的交易进入已验证解释器路径。
  • 直接路径等价：ECDSA 兼容配置与 Ed25519 性能配置各自对照其完整基准执行器。EVM 可作等价性参照和备用实现，不能成为普通转账性能路径必经的仿真步骤。
  • 输出与读取：复用 FrozenShards 和精确父 QMDB 版本；研究紧凑账户索引、热点归并与读集预取，以读次数、复制字节和关键路径解释收益。
  • 传输：不可变认证帧描述 + 有界缺帧补取 + 信用返还。收到描述不能提前报告可执行；数据齐全且认证通过后才能发布执行产物。

4. 候选研究贡献与判定

贡献候选应证明或证伪的主张超出工程移植之处
执行域与复用形式模型共享结果只能在等价执行身份内使用；旧 owner 的迟到发布不会污染新代际；明确哪些故障超出模型。把常见单块缓存抽象为可分析的故障域与生命周期协议，给出反例和安全条件。
确定性依赖调度直接执行在已支持交易集合上与序列基准产生相同状态／gas／回执；热点策略不会改变预定顺序。比较依赖信息利用方式、热点分布与成本模型，找出共享与并行度的交叉点。
有界资源与性能模型队列、等待者、输出引用和接管工作有明确上界；健康／故障路径收益可重复。给出以冲突率、验证者／执行域数、帧大小和状态命中率为变量的模型。

5. 实验、量化目标与失败后仍可产出的结果

  • 基线：序列直接执行、现有并行直接执行、独立 E7、现有 import_once、拟议共享状态机；资源预算固定。Block-STM／NEMO 以可适配的调度策略对照，原论文不同系统数据仅作背景。
  • 负载：均匀独立转账、Zipf 热点、同 sender 长 nonce 链、自转账、跨 sender 收款依赖、费用收款人热点、失败交易和解释器混合。取冲突率 0／10／50／90%，改变线程、帧大小、网络延迟和域数。
  • 故障：owner 在校验前／后取消，结果发布中崩溃，重复与迟到请求，父块分叉，规则版本切换，缺帧、错误结果和超时。模拟模型中的恶意服务必须导致拒绝或独立验证，不能当作 trusted 模型已覆盖。
  • 拟定工程门槛：健康路径每域同身份执行 1 次；安全边界测试零错误复用；至少五组 A/B/A 中成功提交吞吐提高 ≥20% 或 p99 降低 ≥20%，另一项恶化不超过 5%，并报告置信区间。门槛是立项目标，未达到时公开结果。
  • 论文最低闭环：模型／反例、复用协议、等价性证据、可解释的收益与失效区间。即使 E1 吞吐无显著改善，能够证明热点／root／持久化已主导并给出可复现边界，也可构成有价值的负面结果；需经导师评估论文定位。

6. 项目可长期使用的功能

交付 ExecutionArtifact／ExecutionOwner 接口和三个工程适配器、可开启的直接转账路径、可诊断的执行与传输信用指标、父版本绑定与升级失效机制。首版先在单一 Rust 工程验证，再移植到另一 Rust 工程；Go 实现提供独立语义参照与对照执行域，避免要求两名学生重写三套执行器。

课题二 · 建议由数据库 / 分布式可靠性背景学生承担

QMDB 认证状态的跨实现一致性与崩溃安全有界流水

英文暂定：Cross-Implementation Consistency and Crash-Safe Bounded Pipelines for Authenticated Blockchain State

1. 可独立成论文的主问题

如何在三种独立实现和流水运行中，定义可组合的“执行完成、状态认证、共识提交、持久化完成”，使根、回执、恢复水位和可读状态在崩溃／分叉／升级后仍一致，并避免后台写入或状态发布无限落后？

核心假设 H-B：把可观察的状态转移轨迹、精确父版本、持久化发布记录和资源信用合为一个协议，能够保持现有 H2 与 QMDB bin 契约，在限制积压的同时减少读取／发布／写入开销，并系统发现传统“最终余额相同”测试漏掉的根与恢复错误。

2. 拟研究机制

  • 跨实现转移契约：定义账户／slot 编码、零值与删除、操作顺序、append slot 分配、dirty touch、回滚、奖励和失败回执。QMDB append-only 根可能受写入历史影响：最终 KV 相同不能作为根等价的充分条件。逐项以 Gov5 与两个 Rust 实现及真实向量核对。
  • 版本化读视图与发布：执行器只读精确父版本，输出绑定该父版本和有序事务；冻结输出后先计算／校验承诺，再发布供下一块读取。版本 pin、引用释放和 undo 分开管理，根读者与历史读者不混用最新可变视图。
  • 组合恢复记录：将块身份、QMDB 版本／root、回执可用位置、CommitQC、lock 与 R1／R2 持久化投票水位纳入恢复协议。height 与 view 是不同维度，不能直接取数值最小值当作统一进度。
  • 两类日志独立约束：签名释放前仍必须持久化安全投票状态；状态／回执写入可按明确规则流水化，但 durable 确认必须在对应数据和发布记录可恢复后给出。不得通过延迟 vote fsync 或删除安全水位换吞吐。
  • 有界流水：同时限制在途块数、字节、固定版本占用和未持久化输出；用执行、认证与持久化速率反馈 admission／传播信用。缺帧请求单独计费，避免正常投票和恢复消息被大块数据挤占。
  • 可验证快照与恢复：只读导出在同一已认证版本读取 header、QC、账户与 leaf-form；检查配对摘要、根与安全状态，再原子发布 manifest。旧 applied 标记缺失只能按已验证的兼容规则处理，不能推测安全投票记录不存在。
Visible state = (chain/config, canonical block identity, executed version/root, certified block/QC, durable version/root, locked QC, R1 watermark, R2 watermark)

至少给出不变式：可复用读视图的 parent/version 唯一；对外 durable 确认不超出可恢复边界；签名释放后安全水位不会因恢复倒退；拒绝同 view 冲突投票；恢复遇到不一致记录时显式拒绝或进入经验证的追块流程；每类信用的获取和归还恰好对应资源生命周期。

3. 候选研究贡献与创新边界

贡献候选验证办法与已有研究的关系
状态转移轨迹与差分规范生成／缩减三实现差异；对余额相同但触碰／回滚轨迹不同的输入验证 bin 根与恢复结果。QMDB 已研究高效认证存储；本课题研究其接入异构链执行器后的可观察语义与组合正确性。
跨执行／投票／存储的恢复协议建模并枚举写入、flush、rename、fsync、签名及发布边界；构造丢 lock／丢 watermark 的最小反例。近期恢复证书研究给出失忆风险；本课题必须扩展到具体 H2 状态机及 QMDB 多版本发布，而不是把原公式当作完整证明。
带可验证资源界限的流水控制固定资源下增加 offered load、阻塞 IO、掉线补取，检验内存、版本数、积压及 p99 曲线。Zaptos 关注重叠阶段降低延迟；本课题同时约束 durable 边界、版本保留与跨实现恢复。控制器必须有稳定性分析或明确的经验适用范围。

4. 实验、量化目标与成果退路

  • 先复现现有 Go/Rust 导出、hash 参数和 vote 恢复问题，建立最小向量；已修复问题作为回归，不重新宣称新发现。
  • 差分输入至少覆盖普通转账、合约读写、slot 改回原值、嵌套调用回退、交易失败、账户创建／删除、费用和 fork 边界。每个差异缩减为可公开、不含密钥的回归向量。
  • crash-stop 与进程 SIGKILL、故障注入的 fsync／rename 失败分开测；进程退出不等于断电。若要宣称断电／设备错误恢复，需要 VM／块设备故障模拟或专用机器验证。
  • 拟定工程门槛：定义的故障模型下零已确认 durable 交易丢失、零冲突安全投票、三实现共同根／回执一致；在稳定 IO 吞吐范围内积压不超过配置上限；相同语义与持久化策略下 durable TPS 提高 ≥15% 或写放大降低 ≥25%，p99 不恶化超过 5%。均为待验证目标。
  • 功能目标：跨实现导入／导出兼容包、历史状态与证明读取、可认证恢复锚点、按 committed／state-readable／durable 明确区分的运维状态接口。证明是状态查询功能，不作为性能路径 witness 输入。
  • 退路：若数据路径优化收益小，把论文聚焦于通用组合恢复模型、自动差分故障方法和真实漏洞类别；若信用控制本身缺乏创新，将其作为实现支撑而非主要论文贡献。

5. 硕士阶段的范围控制

第一阶段覆盖普通转账和已有真实合约样本，不实现通用新 VM 或新共识；不把全面 Ethereum fork 兼容列入毕业必达。模型先固定七节点 H2／QMDB 配置，再研究 10／16 节点和独立宿主。最终争取形成供三个工程共用的规范、向量与验收接口，而不是维护永久分叉的三套数据库。

必须保留的公平基线

除了“新方案对旧方案”，还应测现有实现经合理调参后的最好稳定基线。对解释器与直接转账的比较，限定相同受支持语义和输入；对 E1 与 E7 的比较，同时报告总资源固定和每节点资源固定两种设置；对异构 Go/Rust 的比较，区分语言／运行时、签名、VM、树和协议差异。

一个方便导师追问的性能模型

系统稳定条件：输入速率低于每个必经阶段的长期服务能力；真实 durable 吞吐受认证、传播、执行、根、共识与持久化中最慢的必要阶段约束。

阶段存在重叠时不要简单相加全部耗时，应分析资源竞争与依赖关键路径。延后写入只会暂时提高可见提交速率；如果积压持续增长，不能宣称获得稳定吞吐提升。

对“重大研究成果”的分层要求
  • 毕业必达：聚焦的问题、可靠原型、明确安全假设、可复现实验和独立论文；不把达到 4.32M TPS 或顶会录用设为毕业条件。
  • 高水平成果：可推广的机制与性质、与强基线对比、故障和边界研究、可公开工件，以及真实三工程采用证据。A 可按贡献考虑 EuroSys／ATC／PPoPP 等；B 可按贡献考虑 SIGMOD／VLDB／FAST／DSN 等。具体投稿窗口和征稿范围在投稿前核对。
  • 联合突破：在明确 fault-domain 与 durable 条件下实现稳定多客户端高吞吐，并证明性能、正确性与恢复可组合；目标是形成长期公共基础设施，而不是一次榜单。
导师与项目方需要投入什么

每人需一名主要导师，执行／数据库方向定期交叉评审；每周一次工程评审，每月一次研究假设和数据评审。现有共享机器可完成同机实验，但多宿主与断电研究需额外隔离机器或 VM／设备模拟环境。至少预留稳定基线、压力运行、冷启动和故障注入的独占窗口。

每个改动保持小提交，代码与实验配置分别归档；私钥和链数据不提交。公开数据集保存合成交易、去敏向量、工件摘要和聚合指标，真实链状态需按可公开范围单独处理。
