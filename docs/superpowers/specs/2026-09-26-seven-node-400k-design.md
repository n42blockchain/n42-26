# Seven-node 400k–600k performance recovery design

Date: 2026-09-26. Scope: n42-26 native H2-v4, QMDB-only seven-validator fleet on the shared quiet host.

## Intent and acceptance

The current valid full-warmup result is 32,010.53 successful committed TPS with builder execution reuse enabled, versus 25,050.88/25,012.18 with it disabled. This is a useful local improvement but an unacceptable global ceiling. The primary target is at least **400,000 successful committed TPS sustained**; 600,000 TPS is the stretch target. Neither target permits skipping transaction signature checks, receipt production, state-root verification, canonical execution or persistence, or five-of-seven CommitQC validation. A leg passes only when all seven nodes agree on committed block hashes and transaction, receipt and state roots, successful receipts are independently counted, failed receipts are reported, and post-run head/restart checks pass. Measure the first 15 seconds and subsequent 15/30-second windows as well as the 60-second total; report host and process resource counters and full configuration hashes.

Use 60 seconds of unscored warmup and same-binary A/B/A for causal comparisons. The shared box-claim controller must pass three quiet checks and own both claims before any build, offline audit or fleet run. Other drivers' claims and processes are never stopped. No result from the older benchmark-bypass chain, Go Gov5, or n42-rs is directly comparable without a workload and validation mapping.

## Evidence and gap

The current 100,000-tx-cap A/B/A is valid: 25,050.88 / 32,010.53 / 25,012.18 TPS, A drift -0.15%, with seven-node QC/receipts/roots passing. For audited transaction-bearing blocks, median build-start-to-broadcast is 1,542 / 1,356 / 1,530 ms, median follower import 655 / 659 / 657 ms, and median leader normalized-payload validation 616 / 426 / 616 ms. Cache reuse saves the duplicate leader execution but does not remove the slower builder and import stages. Source: `docs/benchmarks/20260925-seven-node-rekey-round.md` and the retained warm60 artifacts.

One transaction-bearing B-block trace makes the unexplained gap concrete: packing took 98 ms, builder finish 285 ms, and the payload was built in 431 ms; nevertheless leader validation took another 418 ms before release and build-start-to-broadcast reached about 1.7 seconds. Its follower import took 721 ms, while the next leader's logged commit-to-build-start gap was 2,165 ms. These events overlap different blocks, so their durations must not be added as a single critical path. The block-hash-joined timeline in step 2 will distinguish Engine scheduling, canonical-head readiness, consensus pacing and true idle time.

The historical 170,546.56 TPS n42-26 round53 used trusted pre-signed ingest, `N42_SKIP_TX_VERIFY=1`, and deferred state root; it is not the full H2/QMDB result. Source: `docs/devlog-141-one-minute-rerun-20260901.md`. The n42-rs 429–443k seven-node first windows use a different execution and state path, while its later 538–600k evidence in the reviewed plan is four-node. Source: `docs/n42-rs-7node-optimization-review.md`. The user reports a Gov5 seven-node ~130k result; its exact artifact and validation scope remain to be identified before numerical comparison. An accessible Gov5 cursor39 report instead documents ~43.5k median 30-second windows with unresolved final-state agreement (`../N42-gov5/docs/performance/perf7-cursor39-followup.md`).

A 100k block cap requires at most 250 ms per full committed block for 400k TPS, or 167 ms for 600k. With a 220k cap, the corresponding cadence is 550 ms or 367 ms. These are arithmetic requirements, not projections: increasing the cap alone may worsen execution, networking or audit behavior. A prior 220k attempt failed receipt RPC and large-block fetch limits, so the large-block data and audit path must be fixed before scoring it.

## Approach and order

Three broad approaches were considered. Raising the cap and pacing alone is quickest but cannot pass while 220k block retrieval and receipts fail. Benchmark bypass flags could reproduce older headline rates but violate this design's validity gate. The selected approach is to remove measured production-path latency while keeping full checks, with cap and pacing changes only after each underlying path qualifies.

1. **Reconcile measurement and fix the cap gate.** Freeze binary, workload, genesis, roster, CPU placement and auditor hashes. Locate the reported Go Gov5 run and compare its transaction shape, persistence, root and receipt checks, window definition and hardware. Reproduce the current 100k baseline. Fix large-block RPC/authenticated fetch and receipt pagination or streaming so that 220k committed blocks can be fully audited; test malformed, missing and over-limit responses. Increase the cap only after a seven-node correctness smoke passes.
2. **Profile the whole cadence.** Join each audited block hash to builder pack/EVM/root/finish, leader validation, zstd/serialization/broadcast, follower decode/import/root, voting, FCU and canonical persistence events. Record per-block critical path, overlap and gaps, plus CPU, RSS, faults, disk and network. Select the highest wall-clock contributor, not the largest microbenchmark. Keep invalid/TC, cache-hit and fallbacks visible.
3. **Optimize in bounded rounds.** First qualify the existing parallel builder plus execution reuse at the larger cap. Re-examine parallel follower import only with a same-binary A/B/A and exact root/receipt/restart proof; previous import comparison drifted and is inconclusive. If builder root or finish dominates, reduce redundant QMDB/root work without weakening the root check. If follower import dominates, overlap safe decoding/verification with parent execution or optimize QMDB reads and apply. If view gaps dominate, address backpressure or handoff with the vote and `newPayload(Valid)` boundary intact. Each change gets focused correctness tests and a full seven-node A/B/A before retention.
4. **Stop rules.** Reject any candidate with missing or conflicting receipts/roots, invalid or TC increase, failed post-run verification, uncontrolled hardware overlap, or A-bookend drift that invalidates the comparison. Keep a rollback switch for each retained optimization. Publish achieved TPS, window rates and latency breakdown even if the 400k target remains unmet; never promote a partial or benchmark-bypass number to the target.

## Implementation boundaries

The fleet scripts own launch configuration, cap and audit records. The native payload builder and Reth integration own builder output, root computation and cache reuse. The consensus-service orchestrator owns release of a validated proposal, follower eager import and voting; it must not release a vote before equivalent `newPayload(Valid)` proof. The QMDB provider/patches own state-read and root semantics. Large-block audit transport is separate from consensus data propagation, so its fix must not silently change authenticated block identity. Every code change must identify its owner and preserve the existing serial or standard-execution fallback.

## Verification and completion

Focused tests cover any modified path, including invalid-input and fallback behavior. After release build and local integration tests, one unscored warmup and 60-second A/B/A under the shared claim establish causality. A final independent 60-second qualification at the selected configuration, including all seven nodes' QC, successful receipts, hashes, roots and post-run verification, determines whether 400k is achieved. The 600k stretch uses the same rules. The project remains open until a valid 400k result exists; optimization percentages at 32k are progress evidence only.
