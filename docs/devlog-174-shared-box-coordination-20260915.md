2. 在宿主机上连续三次检查，间隔 30 秒：没有其他重任务，load1 < 8，

3. 同时创建 `/data/blockchain/.box-claim-codex` 和
   `/data/blockchain/wr-logs/.box-claim-codex`，内容为 epoch 秒；随机等待
   20–50 秒，再检查竞争者。按**文件内容**判断优先级，有更早或不明确的竞争者
   就释放自己的 claim，至少等 60 秒。两行“申请时间+心跳”的提议未被共同采用，不启用。
4. 持有期间至少每 30 分钟刷新，监控竞争与资源；只管理自己可验证归属的进程。

## 前台节点监管修复（本轮轻量实现）

`scripts/chain94-fleet.py start --foreground` 现在保持前台运行，持有本次启动的
`Popen` 句柄。任一节点退出（包括退出码 0）都会使监管器报错、向其余节点发送
SIGINT 并等待退出；部分启动失败也清理已经启动的节点。SIGINT/SIGTERM 先记录
取消请求，等已返回的子进程句柄登记后再清理，避免在正常 Popen 返回窗口漏掉节点。
清理超过 60 秒只提示并继续等待，不强杀节点，也不提前退出让外层释放硬件占用锁。
`run.json` 记录 foreground 模式，原有后台启动接口保留。

该模式本身不申请硬件占用权，启动前仍须完成本文件列出的宿主机交接与 claim。
外层 harness 必须等待监管器及其他自有负载进程结束，不能在测量命令退出时就直接
释放 claim。沙箱被强制销毁或 SIGKILL 的生命周期仍不由 Python 信号处理保证。

验证：`python3 -m unittest discover -s scripts -p test_chain94_fleet.py -v`，
12 项通过，约 0.43 秒。新增用例覆盖前台异常退出清理、部分启动失败清理、取消后
等待并恢复信号处理器、慢退出不提前放弃监管。其中异常退出用例启动两个极小的
Python 子进程验证真实回收；其余使用 mock。未启动 N42 节点、网络负载、Cargo
或签名任务。这些检查证明监管行为，不证明四节点网络或 TPS 达标。
