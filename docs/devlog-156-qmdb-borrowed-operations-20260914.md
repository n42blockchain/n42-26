# QMDB 原地排序与借用操作入口

日期：2026-09-14，接续 [devlog-155](devlog-155-qmdb-value-transfer-20260914.md)。
保持 H2 共识、二叉树 QMDB 状态读取/承诺、执行校验与 WAL 同步。
**4 节点 1M TPS 仍未实测达标。**

## 不采用更慢的引用排序

store 原来从借用操作生成 cloned iterator，core 将其收集为完整操作 Vec，再排序、
写树。调用方原有的 Vec 还要用于持久化，因此同时存在两份操作结构。

本轮先试验只排序 `&QmdbOperation`。虽然排序缓冲更小，实测无序输入反而退化：
200k 初始账户的中位耗时 73.853 → 77.685 ms，2M 的 82.635 → 88.750 ms。
这说明更小的排序元素不自动等于更快；比较时需要间接读取 key 可能是原因之一，
本轮没有用硬件计数器证明具体原因。该实现已移除，
[原始实验](benchmarks/20260914-qmdb-borrowed-operations/rejected-reference-sort/)保留。

## 最终实现

- 增加借用入口 `apply_sorted_ops_borrowed` 及记录 undo 的对应入口。严格递增的 key
  直接应用，不分配排序缓冲；非递增输入沿用原来的 owned 排序/重复键检查路径。
  空值与删除保持不同语义；出现重复 key 时仍在任何树修改前拒绝。
- builder normalization 和 import root job 本来就拥有操作 Vec。现在全部操作生成
  完毕后在原 Vec 上排序，再进入 store/树锁。新值复制进树一次，原操作留给 WAL
  和读取版本；没有通过删除同步或校验降低开销。
- store 的候选应用、冷分支重放和启动重放使用借用入口。新生产记录按 key 排序，
  旧日志的任意顺序仍受支持。重复提交仍比较完整操作内容，不只比较父 hash。

WAL 的结构/编码保持兼容，但新记录的操作顺序可以与旧实现不同，因此不声称
新旧 WAL 字节逐字相同。二叉树根和 undo 的槽序列保持一致。现有候选阶段指标
不包含调用方新移到锁外的排序，分析总成本时必须把这一段计入。

## 包含调用方排序的 release 对照

沿用真实 gov5 key/value 编码的合成账户负载：初始 200k 或 2M 个账户，每块更新
147,000 个不同账户；每个配置 6 组交替执行顺序，每进程 3 块。
时间包含调用方排序、操作复制、树修改、undo 和根计算。旧路径 clone 后排序；
新路径先原地排序再借用。不是将排序移出计时区来制造收益。

另外预先准备有序输入作为对照，两边使用相同输入。表中每个中位数来自 18 个块。

| 初始账户 | 输入 | 原中位耗时 | 新中位耗时 | 新耗时相对变化 |
| --- | --- | ---: | ---: | ---: |
| 200k | 无序 | 73.511 ms | 70.790 ms | -3.70% |
| 2M | 无序 | 87.202 ms | 82.578 ms | -5.30% |
| 200k | 已有序 | 62.367 ms | 63.490 ms | +1.80% |
| 2M | 已有序 | 73.763 ms | 72.343 ms | -1.93% |

生产 bundle 遍历生成的操作不保证 key 有序；本轮对无序输入有收益，但不声称所有
输入都更快。已有序输入结果有升有降，且运行没有 CPU 绑定或主机隔离。
这批最终计时在本轮编译和测试完成后才启动，没有主动并行执行本轮其他重负载。
最小/最大值及全部样本见[完整结果](benchmarks/20260914-qmdb-borrowed-operations/results/summary.json)。

独立分配计数程序测得，无论初始输入是否有序，每块均少一个 **8,232,000 bytes**
的分配请求，即 147,000 个 56-byte 操作的临时 Vec。新值的复制仍存在；这里测的是
累计申请字节，不是 RSS 或长期常驻容量。分配计数程序的耗时不进入上述统计。

初始树/输入生成、回滚和再次应用在计时外。每块核对回滚根、append cursor、再次
应用根和全部更新账户值；最终 144 个样本的对应状态根与完整 undo 摘要一致。
测量不包括读取版本、WAL、EVM、网络或 H2，不能外推成整链 TPS。
