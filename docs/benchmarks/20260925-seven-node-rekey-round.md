# Gov5 seven-node execution-reuse round (2026-09-25)

The latest valid native H2/QMDB seven-node A/B/A at a 100,000 transaction block cap measured 23,329.26 / 30,429.96 / 23,541.31 committed successful TPS when parallel payload building was off/on/off. The B uplift was 29.85%; all seven nodes' QC, receipts, and roots passed the audit. The parallel-import comparison was contaminated by a Bitcoin soak that began between A1 and B, so it is not a valid quantitative result. The existing baseline and audit details are in `20260924-seven-node-quiet-hardware.md`.

## Observed critical path

For the sampled 100,000-transaction block 182, the builder packed transactions in 110 ms and produced the payload in 443 ms. Gov5 H2 normalization changed the block hash after building, and the execution bridge evicted the builder's cached output under its original hash. The leader's `newPayload` then re-executed the transactions in 511 ms and recomputed the QMDB root in 209 ms. The complete build-start-to-broadcast interval was 1,622 ms. Follower import was approximately 660–780 ms. The duplicate leader EVM pass was the most direct locally demonstrated waste; the remaining root work and follower import still require measurement after it is removed.

If B improves the leader interval but committed TPS changes little, the next bottleneck is likely follower import, propagation, or view pacing. Compare block 182-style stage timings across A/B/A before changing those paths. The `../n42-rs` seven-node first-window 429–443k TPS is a useful reference for the gap, not a prediction for this different H2/QMDB workload.

## Change and safety gate

The bridge now asks the node-side cache adapter to move the builder output from the original hash to the normalized hash. The adapter accepts only native Cancun payloads whose raw transactions, withdrawals, blob and beacon fields, request profile, and EVM environment inputs are equal across normalization. A failed check or cache miss falls back to the existing execution path. `newPayload(Valid)` is still required before the proposal is released; the existing QC, receipt, and QMDB-root checks remain in force. Set `N42_GOV5_REUSE_BUILDER_EXECUTION=0` for the previous eviction behavior. This switch allows same-binary A/B/A comparisons.

## Validation and next measurement

Focused network and node unit tests cover native normalization, rekeying the output and transaction root, and rejecting changed execution input. The first release binary was built at 2026-09-25 06:36:21 UTC; its SHA-256 was `41fb2a1de1082ac4c1f2139aa41e075162e1f2f640b392a3cad02f70c11efc92`. `scripts/run-native-seven-rekey-round.sh` performs warmup, A1 (reuse off), B (on), A2 (off), each scored leg 60 seconds with parallel build and 100,000 transaction blocks. Run it only through the shared box-claim driver after three quiet checks. Audit each leg's seven nodes, QC, receipts, and state roots before calculating first-window and full-round TPS, A drift, cache-hit frequency, and build-start-to-broadcast latency.

The first release link was interrupted at 2026-09-25 06:13 UTC when another driver acquired the shared hardware claim, then the binary was rebuilt successfully. The user authorized stopping the newly scheduled rBTC seven-day soak to prioritize this measurement; its cron controller and processes were stopped, with data and logs retained. The final network and node focused tests passed, as did the fleet controller's 13 tests and the TPS auditor's 46 tests.

At 07:40 UTC the first warmup acquired the quiet claim and started seven validators, but no node committed a block. Every attempted first empty block was rejected by `newPayload` before proposal: the normalized header claimed the genesis QMDB root `0x427125e2…`, while the validator computed `0x55237e6c…` from a hit in the rekeyed execution cache. The log identified `strategy="synchronous"` on the cache hit, whereas the prior successful run used `strategy="gov5-qmdb"`; Reth's cache-hit branch bypassed the configured custom root strategy. The narrow dependency patch `patches/reth-gov5-cached-state-root.patch` was applied to the local Reth checkout; the project patch application script verifies it. The independent Engine integration target `native_cached_qmdb_builder` passed after its fixture restored the builder output for rekeying, and the release binary SHA-256 became `dba46f47ced897432e6db402de63b9e8b5ba1b80f8ebdac8ca404dcb9b45a780`. The earlier failure logs are retained.

The fixed-binary warmup passed strict seven-node QC/receipt/root audit with 57,344 committed successful transactions. A1, with execution reuse **off**, passed the 60-second strict throughput audit: 1,857,344 successful committed transactions in 61.015524 seconds, or 30,440.52 successful committed TPS; the audit recorded zero QMDB mismatches and zero failed committed transactions. However, the post-audit seven-node chain verification failed. Node 0 received the 7,505,281-byte block at view 212, but its background import failed zstd decompression and left its executed head at view 211 while the other six nodes continued. It had no executed block for its latest CommitQC at the two-second verification grace period. This makes the A1 leg **invalid as a complete seven-node result**, and the driver correctly stopped before B and A2. The audit score must not be used as a measured improvement. Evidence: `.artifacts/native-seven-rekey-fixed-20260925/result-rekey-a1/qualification/summary.tsv`, `verify-after.log`, and `runtime-rekey-a1/logs/node0.log`.

The decoder now retries a failed pooled zstd decode with an independent context before rejecting the frame, resets the pooled context if the retry succeeds, and still rejects a frame that fails both decoders. A focused regression test checks rejection of a damaged frame followed by successful decoding of a valid one. This is a bounded recovery for a possible pooled-context failure, not proof that node 0's bytes were intact: the retained frame was not captured for offline comparison. A new build and valid same-binary A/B/A remain necessary. The shared Gov5 driver acquired the box immediately after this failed leg, so no further heavy build or benchmark has been started.

The logs also show `gov5 RPC block exceeds encoded size limit` and failed authenticated block-by-hash fetches during the 100,000-transaction leg. That RPC currently caps a single block at 1 MiB, below the multi-megabyte blocks in this workload; it cannot serve as a large-block recovery path. This is a separate limit to address if independent decode does not resolve the full-fleet verification failure.

## Full-warmup same-binary round

The shared quiet-hardware controller waited for three clear checks, acquired the claim, ran an unscored 60-second warmup, then ran A1/B/A2 with 60-second scored legs. It released the claim after the driver exited successfully. B exceeded the mean of the two controls by **27.88%**; A2 differed from A1 by **-0.15%**. The first-15-second counts join audited transaction-bearing block hashes and successful receipts to node 0's committed timestamps, relative to each leg's recorded ingest start. Both controls had the same first-window count, while B doubled it. Each strict throughput audit passed with zero failed committed transactions and zero QMDB mismatches. The post-audit check found matching hashes and roots across all seven validators. Only B logged execution-cache hits (1,428 across node logs); none of the three legs logged a pooled zstd retry, payload decompression failure, or unexecutable committed block. This establishes a stable same-binary end-to-end gain for builder execution reuse under this workload and warmup protocol. It does not establish parity with the much higher `../n42-rs` seven-node workload, which uses different execution and state paths.
