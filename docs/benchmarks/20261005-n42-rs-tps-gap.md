# N42 / n42-rs seven-node TPS comparison contract

Captured 2026-10-05 from the source snapshots named in
`.artifacts/n42-rs-tps-gap/reference/`. This is a runner contract and profile
comparison, not a TPS result. The `n42-rs` tree was dirty at freeze; its source
manifest, including the untracked `derive338.py` and `feed338.py`, is the
reference identity. Do not substitute the September handoff values or mutate
that tree.

N42's score window is 60 seconds with four 15-second commit-count windows available
to the timeline and summarizer; the warmed wrapper captures boundaries after the
60-second warmup. Native `n42-rs` defaults to three 30-second windows after 30
seconds of base-fee decay and treats window 1 as the primary measurement. These
are different warmup, window, and acceptance definitions. No scalar comparison
between those native profiles is valid without labelling the difference.

## Frozen native-profile inputs

N42's current warmed wrapper sets seven validators, chain ID 941007, a 220,000
transaction block cap, 512 MiB RPC response limit, `--parallel-build`, QMDB-only
reads, and builder-execution reuse. It uses the frozen `native-seven-20260924-v2`
template and 48-million pre-signed workload. The template manifest identifies a
5-billion gas limit, Cancun profile, 5,000 senders and 147,000 recipients; the
recipient rule is hashed-index distribution. Runtime starts from copied fresh
node datadirs. Strict success still requires the seven-node H2/receipt/root audit
and the post-run seven-node verification; Reth A/B/A additionally checks
post-restart consistency and 5% A-bookend drift.

The checked-in `n42-rs` fleet benchmark defaults are 2,000 senders x 200
transactions each, three 30-second windows, 30-second decay, 32 flood workers,
RPC batch 100, 100,000,000,000,000 wei gas price, and 2,000,000 recipient slots.
Its default transaction is a 21,000-gas transfer. The benchmark tier defaults
to a 480-million gas ceiling, seven separate execution layers for seven
validators, one-second genesis period, 350 ms block interval, and 600 ms
straggler grace. It starts fresh datadirs, decays the base fee, funds a fresh
sender range, then floods; the flood is pinned to the configured flood cores
when `F7_PIN=1`. CPU topology and physical-core/NUMA placement come from the
frozen `fleet7-env.sh` and must be recorded from the actual run environment.

These native profiles differ materially: N42's 5-billion gas block limit and
220k tx/block cap versus n42-rs's default 480-million gas ceiling; N42's
pre-signed sustained stream versus n42-rs's dynamically signed 400k transaction
sender supply; distinct recipient populations and initial state; N42's 60s
warmup and score versus n42-rs's fee-decay plus 90s of windows; and N42's
strict seven-node receipt/QMDB audit versus n42-rs's canonical transaction-log
counter. The documented historical ~429–443k figure is not a current frozen
score and is excluded from this comparison.

## Matched workload feasibility and limits

The closest practical common transaction shape is a legacy/EIP-1559-style
secp256k1 account transfer with 21,000 gas, many sequential-nonce senders,
pre-funded senders, and a deterministic large recipient set. The N42 frozen
input currently has 5,000 senders / 147,000 recipients; n42-rs defaults to
2,000 / 2,000,000. Those values can be parameterized on the n42-rs runner, but
the N42 presigned stream does not establish identical sender/recipient order or
nonce/funding behavior to n42-rs's `tx_flood`; a matched run therefore needs a
new shared transaction manifest or a documented mapping, plus source/config
hashes. Do not call it an identical stream before comparing those exact
transactions.

Both have seven validators, but their consensus protocols, genesis rules,
execution architecture, block interval/timeout, gas/block caps, transaction
submission paths, and validity evidence differ. N42's receipt/QC/QMDB/post-
restart gates must remain mandatory. n42-rs results may be reported only with
its own available acceptance evidence; canonical-log TPS must not be relabelled
as successful receipt TPS. The native and matched-profile reports must keep
these semantics explicit.

## Comparison and invalidation rules

1. Report each repository's valid native result independently, with exact
   source, binary, lock, genesis, roster, workload, runner, launch parameters,
   host placement, claim and resource hashes.
2. A matched-profile result requires seven validators on each side and the
   same transaction sequence, sender count, recipient distribution/account-touch
   shape, gas per transfer, block/gas caps where supported, and scoring window.
   Record any parameter that cannot be aligned as a protocol/profile difference.
3. N42 score counts only transactions with successful receipts in the audited
   committed blocks. A seven-node CommitQC, matching native header/receipt/state
   roots, QMDB-only durable roots, and post-restart agreement are required.
   n42-rs canonical block-log counts are a separate metric unless its own
   receipt-level audit is added and captured.
4. For an A/B/A group, the signed workload, trusted roster, runtime config and
   A binaries must match; the B binary/source must be distinct. Require complete
   score windows, no failed committed transactions, all seven validators,
   post-restart verification, no competing claim/resource mismatch, and both
   total and sustained A-bookend drift <=5%. Otherwise invalidate the group.
5. Shared hardware is scheduled by the common dual-path claim controller. No
   builds, signatures, audits, or fleet starts until the relevant claim is
   visibly granted; run one repository at a time and retain the claim/host
   evidence for each leg.

## Current readiness

The N42 node binary and n42-rs node binaries exist in the frozen manifests, but
their provenance does not establish a match to the frozen full source and lock
hashes. The n42-rs manifest also records `h2_validator` and `tx_flood` as absent
in the checked candidate paths. Do not reuse a binary or launch a run until its
source/build manifest is verified and missing executables are built under a
separate preparation claim. The shared claim controller has not granted a
window in this work, and the checked environment cannot read the `/data` claim
paths. Accordingly, no build, signing, full audit, or benchmark has been run.
