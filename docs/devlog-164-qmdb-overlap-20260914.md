# 普通 import 并行计算 QMDB 根与读取版本

日期：2026-09-14，接续 [devlog-163](devlog-163-qmdb-read-cost-20260914.md)。
**4 节点 1M 成功提交 TPS 仍未实测达标。** 本轮缩短普通 import 中树应用与
不可变读取版本构建的串行等待，保持 H2、二叉树 QMDB、正常执行和耐久发布。

## 吸收上游的独立预读，保留状态身份

复核 Gov5 本周固定提交 `1c365ed9ffc049ecc915c379da706e18851a9682`：它先跨
worker 读取待折叠余额的账户，再沿原顺序完成 fold。测试特意检查 absent 账户、
返回值复制、未命中回落及未写入父状态层的穿透。这些边界比单纯增加 worker 更关键。

本轮没有移植 Go 的账户层或修改 EVM fold，而是在已有精确父块读取版本上应用
相同完整 delta，同时由原提交线程应用二叉树。读取索引不生成另一种状态承诺。
完整上游实现和测试差异已存入证据目录；没有刷新远端引用。

## 并行范围与发布顺序

只有未命中 prepared candidate、父不可变读取版本已缓存、操作数至少 8192，且
独立读取池可用时启用并行。读取关闭或缺少父版本时不会为并行调度提前创建读取池。
小批量、单核或读取池不可用均沿顺序路径；prepared 命中无需再应用树，也不启动
这个任务。缺少父版本仍在根验证后从当前二叉树构建读取索引。

每个 store 的 commit 锁仍覆盖完整提交，最多启动一个 scoped 协调线程。它只
持有父版本 Arc、借用当前操作切片，不克隆完整 delta，不接触可变树或 forest 锁。
索引分片仍使用原来的最多八个专用 worker。没有向可能等待 forest 锁的 EVM
全局池投递任务，避免形成锁和 worker 之间的循环等待。

```mermaid
flowchart LR
    A[精确父版本与完整 delta] --> B[提交线程应用二叉树]
    A --> C[专用线程构建私有读取索引]
    B --> D[等待结束并校验实际根]
    C --> D
    D --> E[编码、写入并同步 WAL]
    E --> F[发布块与读取版本]
```

私有索引暂时携带 header 声称的 root；只有实际二叉树根与它相等且 WAL 同步
成功，才能发布。不是提前接受 header，也不是复用另一块的 EVM 结果。
错误根、重复键、缺失父块、编码/写入错误都丢弃私有结果并沿原路径回滚。
线程创建失败时，提交线程完成树计算后顺序构建读取版本。线程 panic 会传播，
forest 锁随之 poison；不会继续发布一份来源不明的结果。

`n42_qmdb_read_view_overlap_total{outcome=joined|spawn_failed}` 用于观察实际调度。
`joined` 只表示拿到了私有构建结果，之后仍可能因错误根或 WAL 失败拒绝，不能
用作提交数。原 candidate-compute 指标继续包含完整 delta 匹配和协调准备，
不包含 join 等待；read-view-build 指标记录 worker 实际构建时间。两个阶段现在
可能重叠，不能将它们相加计算总耗时。

## 正确性验证

- 节点 QMDB：60 passed、7 ignored；另有实际 provider 读取测试 1 passed。
- 新增两项参数化回归：并行/顺序一致、sibling 与 pinned 父版本隔离、缺失父缓存、
  小批量、prepared 命中、注入线程创建失败；以及错误根、重复键、缺失父块、
  WAL 编码/写入失败、重试、重启后逐键核对。值覆盖删除、空值及 1–80 字节。
- 原 WAL 延迟测试扩展为 8193 条操作，并确认实际 joined：同步期间允许父状态
  读取和推测树计算，待同步块及其读取版本仍不可见，完成后正确发布。
- 独立 release harness：13 passed、2 ignored；包含上述回归、六项 prepared
  candidate 回归及四项读取版本测试。workspace all-targets clippy 通过。

节点检查使用固定补丁 reth `23316e3ff8adca8c3bd5085ff0565fcae019202a`，相邻
开发 reth 未修改。测试中的顺序开关和线程失败注入均为 `cfg(test)`，不增加生产
环境开关。生产开启条件由精确父读取版本、批量大小和可用线程池决定。

## 测量范围与限制

最终对照使用同一个冻结源码的 release 二进制，分别关闭/开启并行派生，其他
树、候选、编码、WAL 写入和 fsync 路径完全相同。200k/2M 初始账户、每块
147k 更新，每个条件六组交替顺序的新进程，每进程三块。账户值使用 Gov5 编码。

普通 import 计时包含输入排序、树应用、读取版本构建、WAL 编码、ext4 写入和
fsync；另行测量 prepared 命中的候选加提交总时间，防止把普通路径收益套到
没有可重叠树工作的命中路径。每个样本核对实际 joined 数、实际根、WAL 长度，
每个进程重开持久化 store 检查最终根与账户 nonce。

普通 import 的总耗时，每格 18 个样本，中位数及范围如下：

| 初始账户 | 顺序构建 | 并行构建 | 中位数变化 |
| --- | ---: | ---: | ---: |
| 200k | 138.660 ms（132.392–159.158） | 102.484 ms（100.121–118.510） | -26.09% |
| 2M | 220.246 ms（208.971–243.201） | 141.470 ms（122.895–252.425） | -35.77% |

按相同进程轮次和块序号对应，200k 的 18/18、2M 的 17/18 并行样本更快。
2M 并行路径仍有一个 252.425 ms 样本，比串行最大值还高；这组数据不证明
尾延迟已经改善，当前测量也不足以将该慢样本归因于某一个阶段。

prepared 命中的旁路控制，计时为候选加提交总时间，每格同样 18 个样本：

| 初始账户 | 测试开关关闭 | 测试开关开启 |
| --- | ---: | ---: |
| 200k | 149.778 ms（145.197–169.582） | 147.356 ms（144.435–158.108） |
| 2M | 230.995 ms（219.548–291.830） | 244.859 ms（213.911–344.792） |

这些样本全部验证 joined=0，两种设置都走同一 prepared 后续路径。2M 控制组
中位数仍上浮约 6%，可见本机测量存在明显波动；当前证据没有隔离其原因。
本轮不为 prepared 路径报告提速，也不据普通提交中位数保证端到端尾延迟。
最终两组共 144 个样本、48 个新进程，全部对应根与 WAL 长度一致且重启校验成功。

EVM、delta 生成/初始复制、初始树和读取版本构建、oracle、重启验证不在计时内。
测量时没有并行编译，没有独占宿主机或绑核。并行消除等待而非所有 CPU 工作，
可能增加并发内存带宽压力；无效根也可能已经消耗读取索引构建工作。本轮没有
测长期 RSS、四节点共同运行时的 CPU 竞争或真实集群缓存命中率。

全部最终样本、源码、二进制 SHA 与验证日志见
[证据目录](benchmarks/20260914-qmdb-overlap/)。首次探索和中止的旧指标口径测量
分别归档，最终结论不使用它们。实际成功提交 TPS 仍需四节点、可信 H2 QC、
原生头和 receipts、QMDB-only 读取，以及持续运行/重启追赶的完整资格检查。
